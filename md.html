1. WordPress core, Gutenberg and Full Site Editing

The core of the interview, alongside testing. FSE isn't on your CV, so practise this section the most.

Q1.How do you approach Gutenberg block development? Walk us through building a custom block.

"I scaffold with create-block, describe everything in block.json, register it from a plugin, and usually render it in PHP. I lean on block supports for styling, and I ship it with tests."

Picture thisA block is like a product in a shop. block.json is the label on the box: name, ingredients (attributes), what it supports, and which files are inside. WordPress reads the label and knows how to stock the shelf. You never have to explain it twice in JS and PHP.

The steps, in the order you'd actually do them:

  1. Scaffold: npx @wordpress/create-block article-teaser gives you a working block, build tooling and block.json.
  2. Describe it in block.json, the single source of truth: name, attributes, supports, editor script, styles, render file.
  3. Register it in PHP with register_block_type( __DIR__ . '/build/article-teaser' ). It lives in a plugin, because if the client changes theme their content shouldn't break.
  4. Pick static or dynamic. For news content that depends on live data, go dynamic (render.php). See Q2.
  5. Use supports (colour, spacing, typography) instead of building your own controls. The block then picks up the design tokens from theme.json for free.
  6. Editor UI: useBlockProps, InspectorControls for the sidebar, @wordpress/components for controls, useSelect to read data.
  7. Be safe: escape in render.php, translate strings, use accessible markup.
  8. Test: PHPUnit for render.php, Jest + RTL for the edit component, one Playwright test for insert-and-publish.

edit.js: useBlockProps, InspectorControls, useSelect plugins/news-uk-practice/src/q01-article-teaser/edit.js
/**
 * Q1, step 6 "Editor UI": what the editor sees and uses inside the block editor.
 *
 * The edit component only runs in the editor. It never decides what readers see:
 * this is a dynamic block, so render.php builds the front-end HTML (Q2).
 * Its job is to let the editor set the block's attributes (postId, showImage)
 * and to show a preview.
 */

// __() marks a string for translation (Q1, step 7 "Be safe": translate strings).
// The second argument is the text domain, which must match block.json "textdomain".
import { __ } from '@wordpress/i18n';

// useBlockProps: the props every block's outer element needs (see below).
// InspectorControls: renders its children in the editor's right-hand sidebar.
import { useBlockProps, InspectorControls } from '@wordpress/block-editor';

// Ready-made, accessible UI from @wordpress/components. Using these instead of
// hand-written inputs gives the standard WordPress look, keyboard support and labels.
import {
	PanelBody,
	Placeholder,
	TextControl,
	ToggleControl,
} from '@wordpress/components';

// useSelect reads data from a @wordpress/data store and re-renders this
// component when that data changes (Q1, step 6: "useSelect to read data").
import { useSelect } from '@wordpress/data';

// core-data is the store that talks to the REST API for posts, users, terms...
import { store as coreStore } from '@wordpress/core-data';

/**
 * WordPress calls Edit with the block's current attributes and a setter.
 *
 * @param {Object}   props
 * @param {Object}   props.attributes    Values defined in block.json "attributes".
 * @param {Function} props.setAttributes Saves new values. Like React's setState,
 *                                       but stored in the block (and the post).
 */
export default function Edit( { attributes, setAttributes } ) {
	const { postId, showImage } = attributes;

	// Fetch the chosen post so the editor sees its title as a preview.
	// - getEntityRecord() fires a REST request the first time and caches the result
	//   in the store, so other blocks asking for the same post don't refetch.
	// - It returns undefined while loading, then the post object.
	// - [ postId ] is the dependency list: the selector re-runs only when postId changes.
	const post = useSelect(
		( select ) =>
			postId
				? select( coreStore ).getEntityRecord(
						'postType',
						'post',
						postId
					)
				: null,
		[ postId ]
	);

	// Input fields give strings; the attribute is declared as "integer" in
	// block.json. Convert here, and clear it (undefined) when the field is emptied,
	// so we never save NaN or "" into a number attribute.
	const onChangePostId = ( value ) => {
		const id = parseInt( value, 10 );
		setAttributes( { postId: Number.isNaN( id ) ? undefined : id } );
	};

	// Defined once, used in two places: the sidebar and the empty-state placeholder.
	// The __next* props opt in to the current component styles (they silence
	// deprecation warnings and will become the default).
	const idControl = (
		<TextControl
			__next40pxDefaultSize
			__nextHasNoMarginBottom
			label={ __( 'Post ID', 'news-uk' ) }
			type="number"
			value={ postId ?? '' }
			onChange={ onChangePostId }
		/>
	);

	return (
		/*
		 * Why useBlockProps() is needed:
		 * The block editor has to be able to find, select and style this block.
		 * useBlockProps() returns the props that make that work, and they must be
		 * spread on the block's OUTERMOST element:
		 * - className "wp-block-news-uk-article-teaser" (generated from the block name)
		 *   plus classes from block supports, e.g. "has-accent-background-color",
		 * - inline styles from supports (padding, colours) so the editor preview
		 *   matches the front end,
		 * - the data-block id, the "Block: Article Teaser" accessibility label,
		 *   focus handling and the ref the editor uses to select the block.
		 * With apiVersion 3 (block.json) the editor does NOT add a wrapper for you,
		 * so without this the block can't be clicked/selected and supports don't apply.
		 * On the PHP side, get_block_wrapper_attributes() in render.php is the twin
		 * of this: same classes and styles on the front end.
		 */
		<div { ...useBlockProps() }>
			{ /* Sidebar settings (Settings tab in the block inspector). */ }
			<InspectorControls>
				<PanelBody title={ __( 'Settings', 'news-uk' ) }>
					{ idControl }
					<ToggleControl
						__nextHasNoMarginBottom
						label={ __( 'Show image', 'news-uk' ) }
						checked={ !! showImage }
						onChange={ ( value ) =>
							setAttributes( { showImage: value } )
						}
					/>
				</PanelBody>
			</InspectorControls>

			{ /* Empty state: no post chosen yet, so ask for one in the block itself. */ }
			{ ! postId && (
				<Placeholder
					label={ __( 'Article Teaser', 'news-uk' ) }
					instructions={ __(
						'Enter the ID of the post to link to.',
						'news-uk'
					) }
				>
					{ idControl }
				</Placeholder>
			) }

			{ /* A post is chosen but the REST request hasn't returned yet. */ }
			{ postId && ! post && <p>{ __( 'Loading…', 'news-uk' ) }</p> }

			{ /*
			 * Preview of the title. React escapes text automatically, so no
			 * escaping is needed here (unlike render.php, where we must escape).
			 * title.raw exists when the user can edit the post; otherwise fall
			 * back to the rendered title.
			 */ }
			{ post && (
				<p className="news-uk-article-teaser__title">
					{ post.title?.raw || post.title?.rendered }
				</p>
			) }
		</div>
	);
}
render.php: escape everything, return nothing for bad input plugins/news-uk-practice/src/q01-article-teaser/render.php
<?php
/**
 * Server-side render for news-uk/article-teaser (Q1, step 4 "dynamic"; Q2).
 *
 * WordPress includes this file every time the block appears on a page, with
 * three variables already set:
 *
 * @var array    $attributes Block attributes (postId, showImage, plus any
 *                           supports values such as colours and padding).
 * @var string   $content    Inner content. Unused: this block has no InnerBlocks.
 * @var WP_Block $block      The block instance (gives context, e.g. the current postId).
 *
 * Whatever this file prints becomes the block's HTML. Printing nothing removes
 * the block from the page.
 *
 * @package News_UK_Practice
 */

// Variables here are global-scope, so they get a prefix (news_uk_) to avoid
// clashing with other code. PHPCS (WordPress rules) enforces this (Q9).
$news_uk_post = empty( $attributes['postId'] ) ? null : get_post( (int) $attributes['postId'] );

// Refuse bad input (what Q11's tests check): missing, deleted, draft, private
// or trashed posts render nothing, so readers never see a broken or secret link.
if ( ! $news_uk_post || 'publish' !== $news_uk_post->post_status ) {
	return;
}
?>
<?php
/*
 * get_block_wrapper_attributes() is the PHP twin of useBlockProps() in edit.js.
 * It outputs class="wp-block-news-uk-article-teaser ..." plus the classes and
 * inline styles from block supports (colour, padding, font size), so the front
 * end matches the editor. The extra 'class' is merged in. Its output is
 * already escaped by core, hence the phpcs:ignore.
 */
?>
<div <?php echo get_block_wrapper_attributes( [ 'class' => 'news-uk-article-teaser' ] ); // phpcs:ignore WordPress.Security.EscapeOutput.OutputNotEscaped -- Escaped by core. ?>>
	<?php if ( ! empty( $attributes['showImage'] ) && has_post_thumbnail( $news_uk_post ) ) : ?>
		<?php
		// Core builds a safe <img> with srcset/sizes (responsive images, Q18).
		// loading="lazy": teasers are rarely the first thing on screen.
		echo get_the_post_thumbnail( $news_uk_post, 'thumbnail', [ 'loading' => 'lazy' ] );
		?>
	<?php endif; ?>
	<?php
	/*
	 * Escape late, at the point of output (Q1 step 7, Q9):
	 * - esc_url() for URLs in attributes,
	 * - esc_html() for text. A title like "<script>" is shown as text, not run.
	 * The title and link are read now, so a headline edit shows up on every page
	 * that uses this teaser without anyone re-saving those pages.
	 */
	?>
	<a class="news-uk-article-teaser__link" href="<?php echo esc_url( get_permalink( $news_uk_post ) ); ?>">
		<?php echo esc_html( get_the_title( $news_uk_post ) ); ?>
	</a>
</div>
index.js: what each block.json key means plugins/news-uk-practice/src/q01-article-teaser/index.js
/**
 * Q1: the editor-side entry point for the Article Teaser block.
 *
 * block.json is the single source of truth (Q1, step 2). JSON can't hold
 * comments, so here is what each key in ./block.json means:
 * - "apiVersion": 3     Current block API. The editor canvas runs in an iframe
 *                       and the block must use useBlockProps() itself.
 * - "name"              "namespace/block-name". Stored in post content as
 *                       <!-- wp:news-uk/article-teaser {...} /-->. Never rename.
 * - "attributes"        The block's data and its types. Saved in that comment.
 * - "supports"          Features WordPress adds for free (Q1, step 5): here
 *                       colours, padding and font size, using theme.json tokens.
 *                       "html": false hides "Edit as HTML" (no static HTML).
 * - "textdomain"        For translations (__() in JS, __() in PHP).
 * - "editorScript"      This file, built to build/q01-article-teaser/index.js.
 * - "style"             CSS loaded on the front end AND in the editor, and only
 *                       on pages that contain the block.
 * - "render"            PHP file that builds the front-end HTML: a dynamic block.
 *
 * The same block.json is read by PHP (register_block_type in load.php) and by
 * JS (imported below), so names and attributes are never defined twice.
 */
import { registerBlockType } from '@wordpress/blocks';
import metadata from './block.json';
import Edit from './edit';

// Importing the stylesheet tells the build (wp-scripts) to compile style.scss
// into style-index.css, the file block.json "style" points to.
import './style.scss';

registerBlockType( metadata.name, {
	edit: Edit,
	// Dynamic block (Q2): save() returns null, so post_content stores only the
	// block comment with its attributes, and render.php builds the HTML on every
	// request. Changing the markup later needs no deprecations (Q3).
	save: () => null,
} );

Q2.When do you choose a static block and when a dynamic block? What are the trade-offs?

"Static if the content is final when the editor clicks Save. Dynamic if it depends on live data or the markup might change later. For News UK, anything data-driven would be dynamic by default."

Picture thisStatic is a printed newspaper: the words are fixed on the page the moment it's printed. Dynamic is a TV screen in a shop window: the frame stays the same, but what it shows is fetched fresh each time someone looks.
StaticDynamic
Where the HTML comes fromJS save() writes it into post_contentsave returns null; PHP (render.php) builds it on every request
Good forA styled callout, a quote box: content known at save timeLatest articles, author bio, paywall state, prices: anything that changes after publishing
SpeedVery fast, no PHP workCosts PHP per request, so cache queries in the object cache. The edge cache helps too.
Changing markup laterPainful: needs deprecations or every old post shows "invalid block"Easy: edit render.php and every post updates

Hybrid: a dynamic block with InnerBlocks saves only <InnerBlocks.Content />. render.php receives that as $content and wraps it. For example, a "Live Blog Entry" where the editor writes the paragraphs and PHP adds the live timestamp and wrapper.

Example"A 'Related Articles' block on The Times. If it were static, the three links would be frozen. When one of those articles is unpublished, you'd have a dead link in thousands of posts. As a dynamic block it always shows current, published articles."
Remember it as"Will it still be true tomorrow?" If yes, static. If not sure, dynamic. And never an unclear mix: a block either has a real save or it's dynamic.
Your storyYour product/affiliate blocks: prices and links change after publishing, so they render from live, cached data.

/**
 * Q2, STATIC example: Feature Card, a box that holds other blocks.
 *
 * Static means save() below produces the final HTML when the editor clicks
 * Save, and that HTML is stored in post_content. On the front end WordPress
 * just prints it: no PHP runs for this block (fast, Q2 table "Speed").
 * The price: if save() changes later, old posts no longer match and need a
 * deprecation (Q3).
 *
 * It is also the practice plan's "one block with InnerBlocks".
 */
import { registerBlockType } from '@wordpress/blocks';
import { useBlockProps, useInnerBlocksProps } from '@wordpress/block-editor';
import metadata from './block.json';
import './style.scss';

// Only these blocks can go inside the card: keeps the design intact
// (the "locked design" reason in Q8).

Q3.What are block deprecations? Walk us through changing the markup of a static block safely.

"A deprecation is a record of how a block used to be saved, so the editor can recognise old content and upgrade it instead of calling it broken."

Picture thisThe editor is a strict checker. When it opens a post it re-runs today's save() and compares the result with what's stored, like comparing a signature. If you changed save(), old posts no longer match and you get "This block contains unexpected or invalid content." Deprecations are like keeping your old signatures on file: "if it looks like this, it's still me, here's how to update it."

How to change markup safely:

  1. Copy the current save, attributes and supports into a new entry at the top of the deprecated array. It's a frozen snapshot: paste the old code, never import the live function.
  2. Change the real save to the new markup.
  3. If the data shape changed (for example url renamed to href), add migrate( attributes, innerBlocks ). Use isEligible() if you need to force an upgrade on blocks that still validate.
  4. Add a Jest test: parse the old markup and assert the block is valid and migrated.
const v1 = {
  attributes: { url: { type: 'string' } },
  save: ( { attributes } ) => <a className="cta" href={ attributes.url }>Read</a>,
  migrate: ( { url } ) => ( { href: url } ),
};
registerBlockType( 'md/cta', { ...metadata, edit, save, deprecated: [ v1 ] } );

Gotcha: posts only upgrade when someone opens and saves them. Until then the front end still serves the old HTML, so your CSS has to support both versions for a while.

Remember it as"Freeze, Change, Migrate, Test." Newest deprecation first. If the markup keeps changing, go dynamic and the problem disappears.

 * Q3, step 4 "Add a Jest test": prove old content is upgraded, not broken.
 *
 * Instead of pasting old HTML by hand, the test REGISTERS v1 and serializes a
 * block with it, so the fixture is exactly what v1 produced. Then it registers
 * the real (v2) block and parses that HTML like the editor would when an old
 * post is opened.
 */

/**
 * WordPress dependencies
 */
import {
	registerBlockType,
	unregisterBlockType,
	createBlock,
	serialize,
	parse,
} from '@wordpress/blocks';

/**
 * Internal dependencies
 */
import { settings } from '../settings';
import deprecated from '../deprecated';

const NAME = 'news-uk/cta';

// Produce content exactly as v1 of the plugin saved it: register a block that
// has only v1's attributes and save(), serialize, then unregister it again.
function savedByV1( attributes ) {
	const [ v1 ] = deprecated;
	registerBlockType( NAME, {
		apiVersion: 3,
		title: 'CTA v1',
		category: 'design',
		attributes: v1.attributes,
		save: v1.save,
	} );
	const html = serialize( createBlock( NAME, attributes ) );
	unregisterBlockType( NAME );
	return html;
}

describe( 'CTA deprecations', () => {
	afterEach( () => unregisterBlockType( NAME ) );

	// The core promise: an old post opens cleanly and its data is migrated
	// (url -> href) by migrate() in deprecated.js.
	it( 'upgrades v1 content instead of marking it invalid', () => {
		const oldHtml = savedByV1( { url: 'https://example.com/story' } );
		expect( oldHtml ).toContain(
			'<a class="cta" href="https://example.com/story">Read</a>'
		);

		registerBlockType( NAME, settings );
		const [ block ] = parse( oldHtml );

		expect( block.isValid ).toBe( true );
		expect( block.attributes ).toEqual( {
			href: 'https://example.com/story',
			text: 'Read',
		} );
		// The editor logs each successful upgrade.
		expect( console ).toHaveInformed();
	} );

	// After the editor upgrades it, the next save writes v2 markup.
	it( 'saves the new markup once upgraded', () => {
		const oldHtml = savedByV1( { url: 'https://example.com/story' } );
		registerBlockType( NAME, settings );
		const [ block ] = parse( oldHtml );

		expect( console ).toHaveInformed();

		registerBlockType( NAME, settings );

			createBlock( NAME, { href: '/x', text: 'Go' } )
		);
		const [ block ] = parse( html );

		expect( block.isValid ).toBe( true );
		expect( block.attributes ).toEqual( { href: '/x', text: 'Go' } );
	} );
} );

Q5.How do you add front-end interactivity to a block without shipping React to readers?

"The Interactivity API: PHP renders normal HTML with a few data-wp-* attributes, and a tiny shared script brings it to life. Readers get fast, cacheable HTML and very little JavaScript."

Picture thisThe HTML is a light switch already wired into the wall. The data-wp-on--click attribute says "this switch controls that light". The small store is the fuse box. You don't ship a whole power station (React) to every reader just to flip one light.
<div data-wp-interactive="md/accordion" <?php echo wp_interactivity_data_wp_context( [ 'open' => false ] ); ?>>
  <button data-wp-on--click="actions.toggle" data-wp-bind--aria-expanded="context.open">Show more</button>
  <div data-wp-bind--hidden="!context.open">Hidden text</div>
</div>

// view.js (loaded via "viewScriptModule" in block.json)
import { store, getContext } from '@wordpress/interactivity';
store( 'md/accordion', { actions: { toggle() { const c = getContext(); c.open = ! c.open; } } } );
  • Why: the HTML is server-rendered, so it works with SEO and edge caching. The JS runtime is small and shared across all blocks. Initial state can be set in PHP with wp_interactivity_state().
  • Small one-offs: a plain viewScript with vanilla JS is fine. No jQuery in new code.
  • Accessibility: real <button>s, keep aria-expanded in sync, manage focus, test with the keyboard.
Remember it as"HTML first, sprinkle behaviour." Directives in markup, a small store in a script module.

/**
 * Server-side render for news-uk/accordion.
 *
 * Directives (data-wp-*) are processed on the server too, so the first HTML
 * already has the right hidden/aria-expanded values: works without JS for SEO
 * and edge caching, and does not flash.
 *
 * @var array    $attributes Block attributes.
 * @var string   $content    Inner content (unused).
 * @var WP_Block $block      Block instance.
 *
 * @package News_UK_Practice
 */

// Nothing to reveal: render nothing rather than a button that opens an empty panel.
if ( '' === trim( $attributes['body'] ?? '' ) ) {
	return;
}

// A unique id per accordion, so aria-controls points at the right panel even
// when there are several accordions on one page.
$news_uk_panel_id = wp_unique_id( 'news-uk-accordion-' );

/*
 * How the directives below work (Q5, "light switch wired into the wall"):
 *
 * data-wp-interactive="news-uk/accordion"
 *     "This element and its children are controlled by the store named
 *     news-uk/accordion" (the store() in view.js).
 *
 * wp_interactivity_data_wp_context( [ 'isOpen' => false ] )
 *     Prints data-wp-context='{"isOpen":false}': state that belongs to THIS
 *     accordion only, so two accordions on a page open independently.
 *
 * data-wp-on--click="actions.toggle"
 *     On click, run actions.toggle from the store (flips context.isOpen).
 *
 * data-wp-bind--aria-expanded="context.isOpen"
 * data-wp-bind--hidden="!context.isOpen"
 *     Keep these attributes in sync with context.isOpen. The runtime updates
 *     them whenever the value changes; no manual DOM code.
 *
 * WordPress also processes these directives in PHP before sending the page, so
 * the first HTML already says aria-expanded="false" and has "hidden" on the panel.
 * Readers without JS, search engines and the edge cache all get correct HTML.
 *
 * Accessibility: a real <button> (keyboard and screen reader for free),
 * aria-expanded kept in sync, aria-controls linking button and panel.
 */
?>
<div
	<?php echo get_block_wrapper_attributes(); // phpcs:ignore WordPress.Security.EscapeOutput.OutputNotEscaped -- Escaped by core. ?>
	data-wp-interactive="news-uk/accordion"
	<?php echo wp_interactivity_data_wp_context( [ 'isOpen' => false ] ); // phpcs:ignore WordPress.Security.EscapeOutput.OutputNotEscaped -- Escaped by core. ?>
>
	<button
		type="button"
		aria-controls="<?php echo esc_attr( $news_uk_panel_id ); ?>"
		data-wp-on--click="actions.toggle"
		data-wp-bind--aria-expanded="context.isOpen"
	>
		<?php echo esc_html( $attributes['label'] ); ?>
	</button>
	<div id="<?php echo esc_attr( $news_uk_panel_id ); ?>" data-wp-bind--hidden="!context.isOpen">
		<?php
		// body comes from a RichText field, so it may contain safe inline HTML
		// (bold, links). wp_kses_post() keeps that and strips anything unsafe.
		echo wp_kses_post( $attributes['body'] );
		?>
	</div>
</div>

/**
 * Q5: the accordion's ENTIRE front-end JavaScript (about 140 bytes built).
 *
 * Loaded as a script module (block.json "viewScriptModule") only on pages that
 * contain the block. The markup already exists (render.php); this only says
 * what happens on click. The shared @wordpress/interactivity runtime is loaded
 * once per page and used by every interactive block, instead of each block
 * shipping its own React.
 */
import { store, getContext } from '@wordpress/interactivity';

// The store name must match data-wp-interactive="news-uk/accordion" in render.php.
store( 'news-uk/accordion', {
	actions: {
		// Called by data-wp-on--click="actions.toggle".
		toggle() {
			// getContext() returns the data-wp-context of the accordion that was
			// clicked (not a global), so each accordion keeps its own isOpen.
			const context = getContext();
			// The context is reactive: changing it makes the runtime update every
			// data-wp-bind--* that reads isOpen (aria-expanded, hidden).
			context.isOpen = ! context.isOpen;
		},
	},
} );

"theme.json sets the design rules, templates and parts set the structure, patterns and blocks fill it in. To customise, I start with the lightest tool and only go heavier when I need to."

 * Q11: PHPUnit tests for the dynamic Article Teaser block (q01).
 *
 * Checklist: Exists, Works, Refuses, Safe.
 *

namespace News_UK_Practice\Tests;

use WP_UnitTestCase;

/**
 * Article Teaser tests.
 */
class Article_Teaser_Test extends WP_UnitTestCase {

	/**
	 * Render the block the way WordPress does on the front end.
	 *
	 * @param array $attributes Block attributes.
	 * @return string
	 */
	private function render( array $attributes ) {
		// Cast to object: an empty PHP array encodes as [] (not a valid block
		// comment), an empty object as {}.
		return do_blocks( '<!-- wp:news-uk/article-teaser ' . wp_json_encode( (object) $attributes ) . ' /-->' );
	}

	/**
	 * Exists: registered from block.json, with its attributes.
	 */
	public function test_block_is_registered() {
		$block = \WP_Block_Type_Registry::get_instance()->get_registered( 'news-uk/article-teaser' );

		$this->assertNotNull( $block );
		$this->assertArrayHasKey( 'postId', $block->attributes );
		$this->assertTrue( $block->is_dynamic() );
	}

	/**
	 * Works: a published post renders as a link with the current title.
	 */
	public function test_renders_link_to_published_post() {
		$post_id = self::factory()->post->create( [ 'post_title' => 'Budget day live' ] );

		$html = $this->render( [ 'postId' => $post_id ] );

		$this->assertStringContainsString( 'href="' . get_permalink( $post_id ) . '"', $html );
		$this->assertStringContainsString( 'Budget day live', $html );
	}

	/**
	 * Works: the title is live, not frozen at save time.
	 */
	public function test_shows_updated_title_without_resaving() {
		$post_id = self::factory()->post->create( [ 'post_title' => 'Old headline' ] );
		wp_update_post(
			[
				'ID'         => $post_id,
				'post_title' => 'New headline',
			]
		);

		$this->assertStringContainsString( 'New headline', $this->render( [ 'postId' => $post_id ] ) );
	}

	/**
	 * Refuses: anything that is not a published post renders nothing.
	 *
	 * Data providers run before the test's DB transaction starts, so they pass
	 * plain values and the test creates the posts (otherwise they would leak).
	 *
	 * @dataProvider bad_posts
	 *
	 * @param string|int|null $input A post status to create, or a raw postId.
	 */
	public function test_renders_nothing_for_bad_input( $input ) {
		$attributes = [];
		if ( is_string( $input ) ) {
			$attributes['postId'] = self::factory()->post->create( [ 'post_status' => $input ] );
		} elseif ( null !== $input ) {
			$attributes['postId'] = $input;
		}

		$this->assertSame( '', trim( $this->render( $attributes ) ) );
	}

	/**
	 * One test, every edge case.
	 *
	 * @return array
	 */
	public static function bad_posts() {
		return [
			'draft'      => [ 'draft' ],
			'private'    => [ 'private' ],
			'trashed'    => [ 'trash' ],
			'missing ID' => [ 999999 ],
			'zero'       => [ 0 ],
			'no ID'      => [ null ],
		];
	}

	/**
	 * Safe: HTML in a title is escaped, not executed.
	 */
	public function test_escapes_title() {
		// WordPress's kses filter would strip <script> on save, so the render
		// code would never see it. Turn kses off to simulate bad data that got in
		// another way (an import, direct DB write): escaping must still hold.
		kses_remove_filters();
		$post_id = self::factory()->post->create( [ 'post_title' => 'Budget <script>alert(1)</script>' ] );
		kses_init_filters();

		$html = $this->render( [ 'postId' => $post_id ] );

		$this->assertStringNotContainsString( '<script>', $html );
		$this->assertStringContainsString( '&lt;script&gt;', $html );
	}

	/**
	 * Supports: block supports add their classes/styles to the wrapper.
	 */
	public function test_supports_add_wrapper_classes_and_styles() {
		$post_id = self::factory()->post->create();

		$html = $this->render(
			[
				'postId'          => $post_id,
				'backgroundColor' => 'accent',
				'style'           => [ 'spacing' => [ 'padding' => [ 'top' => '20px' ] ] ],
			]
		);

		$this->assertStringContainsString( 'wp-block-news-uk-article-teaser', $html );
		$this->assertStringContainsString( 'has-accent-background-color', $html );
		$this->assertStringContainsString( 'padding-top:20px', $html );
	}

	/**
	 * The showImage toggle adds the featured image only when asked.
	 */
	public function test_show_image_toggle() {
		$post_id = self::factory()->post->create();
		$image   = self::factory()->attachment->create_upload_object( DIR_TESTDATA . '/images/canola.jpg', $post_id );
		set_post_thumbnail( $post_id, $image );

		$this->assertStringNotContainsString( '<img', $this->render( [ 'postId' => $post_id ] ) );
		$this->assertStringContainsString(
			'<img',
			$this->render(
				[
					'postId'    => $post_id,
					'showImage' => true,
				]
			)
		);
	}

Q12.Do you know the testing pyramid method?

"Lots of fast unit tests at the bottom, fewer integration tests in the middle, a handful of end-to-end tests on top, all sitting on static analysis."

Picture thisChecking a car. Unit tests are checking each bolt and spark plug on the bench: cheap, fast, thousands of them. Integration tests check the engine runs once assembled. E2E is a test drive: realistic but slow and expensive, so you only do a few. You wouldn't find a loose bolt by test-driving 500 times.
            /\        E2E (Playwright)                 few, slow, realistic
           /  \
          /----\      Integration (WP_UnitTestCase,    some
         /      \     REST, block rendering)
        /--------\
       /          \   Unit (PHPUnit, Jest)             many, fast
      /------------\
      Static analysis (PHPCS, PHPStan, ESLint)         foundation

Why this shape: going up, tests get slower, more expensive and flakier. At the bottom you get feedback in seconds.

Anti-pattern: the "ice cream cone", the pyramid upside down: mostly manual or E2E testing and hardly any unit tests. Slow, flaky, and bugs are found late.

Remember it as"Many small, few big." Upside down it's an ice cream cone, and that melts.

Q18.Describe your overall caching strategy and approach to performance optimization.

"Cache at every layer, make the queries that remain cheap, keep slow work out of the page request, and measure rather than guess. Any uncached expensive operation in a request is a bug."

Picture thisGetting a coffee. Fastest: you already have one in your hand (browser cache). Next: the kiosk at the station has it ready (CDN/edge). Next: the café has a pot brewed (object cache). Slowest: grind the beans from scratch (database query). Make sure almost nobody has to grind beans.

1. Layers: browser, then CDN/edge (whole pages), then object cache (fragments and query results), then efficient DB queries.

2. Cheap queries:

  • 'no_found_rows' => true when not paginating (skips counting every match)
  • Bounded posts_per_page, never -1
  • 'fields' => 'ids' when you only need IDs

function latest_ids_in_category( $category_id, $limit = 5 ) {
	$key = 'latest_' . (int) $category_id . '_' . (int) $limit . '_' . wp_cache_get_last_changed( 'posts' );
	$ids = wp_cache_get( $key, 'news_uk' );

		$ids = get_posts( latest_ids_args( $category_id, $limit ) );
		wp_cache_set( $key, $ids, 'news_uk', 5 * MINUTE_IN_SECONDS );
	}

	return $ids;
}

 *   └── SearchResults (queries posts; asks Edit to add one)

import { useBlockProps } from '@wordpress/block-editor';
import { SearchControl } from '@wordpress/components';
import { useSelect } from '@wordpress/data';
import { store as coreStore } from '@wordpress/core-data';
// @wordpress/element is WordPress's wrapper around React: same hooks, and it
// uses the copy of React already loaded in the editor (no second React).
import { useState, useCallback } from '@wordpress/element';
import { __ } from '@wordpress/i18n';
import useDebouncedValue from './use-debounced-value';
import SearchResults from './search-results';
import SelectedList from './selected-list';

export default function Edit( { attributes, setAttributes } ) {
	// The chosen post IDs, in order. Stored in the block (block.json attribute),
	// so this is the single source of truth for both child lists.
	const { postIds } = attributes;

	// Controlled input: React state holds the value and the input only displays
	// it. Every keystroke goes through setSearch, so we can also clear it
	// programmatically (see add()).
	const [ search, setSearch ] = useState( '' );

	// The search term, but only once typing pauses for 300ms. Without this,
	// every keystroke would fire a REST request.
	const debouncedSearch = useDebouncedValue( search, 300 );

	// Titles for the chosen IDs. Keep useSelect results small and plain: here,
	// an array of strings. useSelect compares results shallowly, so when the
	// store changes for unrelated reasons (another block, a typing indicator...),
	// an array of the same strings does NOT re-render this component.
	// Returning whole post objects would re-render far more often.
	const titles = useSelect(
		( select ) =>
			postIds.map(
				( id ) =>
					select( coreStore ).getEntityRecord(
						'postType',
						'post',
						id
					)?.title?.rendered || `#${ id }` // Placeholder while loading.
			),
		[ postIds ] // Re-run the selector only when the list of IDs changes.
	);
	const items = postIds.map( ( id, i ) => ( { id, title: titles[ i ] } ) );

	// Lifted state: SelectedList and SearchResults both need to change postIds,
	// so the logic lives here in their common parent and they get callbacks.
	// They don't know about attributes at all: easy to reuse and to test.

	// useCallback keeps the same function between renders unless postIds
	// changes, so a memoised child wouldn't re-render needlessly.
	const add = useCallback(
		( id ) => {
			// Never mutate attributes: always pass a NEW array, otherwise React
			// and the block editor can't see that anything changed.
			setAttributes( { postIds: [ ...postIds, id ] } );
			setSearch( '' ); // Controlled input: clearing it is just setting state.
		},
		[ postIds, setAttributes ]
	);
	const remove = ( id ) =>
		setAttributes( { postIds: postIds.filter( ( x ) => x !== id ) } );
	const moveUp = ( index ) => {
		const next = [ ...postIds ]; // Copy, then swap two neighbours.
		[ next[ index - 1 ], next[ index ] ] = [
			next[ index ],
			next[ index - 1 ],
		];
		setAttributes( { postIds: next } );
	};

	return (
		// useBlockProps: the block's selectable wrapper (see q01 edit.js).
		<div { ...useBlockProps() }>
			<SelectedList
				items={ items }
				onMoveUp={ moveUp }
				onRemove={ remove }
			/>
			<SearchControl
				__nextHasNoMarginBottom
				label={ __( 'Search posts', 'news-uk' ) }
				value={ search }
				onChange={ setSearch }
			/>
			<SearchResults
				search={ debouncedSearch }
				excludeIds={ postIds }
				onSelect={ add }
			/>
		</div>
	);
}

import { useEffect, useState } from '@wordpress/element';

/**
 * Returns `value`, but only after it has stopped changing for `delay` ms.
 *
 * useEffect dependencies: everything the effect reads (value, delay).
 * Cleanup: cancel the pending timer when value changes or on unmount,
 * otherwise old timers fire with stale values.
 *
 * @param {*}      value Value to debounce.
 * @param {number} delay Milliseconds.
 * @return {*} Debounced value.
 */
export default function useDebouncedValue( value, delay = 300 ) {
	const [ debounced, setDebounced ] = useState( value );

	useEffect( () => {
		const timer = setTimeout( () => setDebounced( value ), delay );
		return () => clearTimeout( timer );
	}, [ value, delay ] );

	return debounced;
}

 * content (REST API); this separate Node app draws the pages.
 *
 *   node plugins/news-uk-practice/src/q24-headless/render-service.mjs
 *   open http://localhost:3001/article/<post-slug>
 *
 * Note everything it has to rebuild that WordPress gave us for free: routing,
 * escaping, the template, 404s, caching headers, SEO tags.
 */
import { createServer } from 'node:http';

const WP = process.env.WP_URL || 'http://localhost:8080';
const PORT = Number( process.env.PORT || 3001 );

const escape = ( value ) =>
	String( value ).replace(
		/[&<>"']/g,
		( c ) =>
			( {
				'&': '&amp;',
				'<': '&lt;',
				'>': '&gt;',
				'"': '&quot;',
				"'": '&#39;',
			} )[ c ]
	);

async function getArticle( slug ) {
	// Ask only for the fields the page needs (REST's answer to GraphQL field selection).
	const url = new URL( '/wp-json/wp/v2/posts', WP );
	url.searchParams.set( 'slug', slug );
	url.searchParams.set( '_fields', 'title,content,link,news_uk' );

	const response = await fetch( url, {
		signal: AbortSignal.timeout( 3000 ),
	} );
	if ( ! response.ok ) {
		throw new Error( `WordPress returned ${ response.status }` );
	}
	const [ post ] = await response.json();
	return post;
}

function page( post ) {
	return `<!doctype html>
<html lang="en"><head><meta charset="utf-8">
<title>${ escape( post.title.rendered ) }</title>
<link rel="canonical" href="${ escape( post.news_uk.canonical ) }">
</head><body>
<h1>${ post.title.rendered }</h1>
<p><em>${ escape( post.news_uk.standfirst ) }</em> · ${ post.news_uk.reading_time } min read</p>
${ post.content.rendered }
<footer>Rendered by the headless render service</footer>
</body></html>`;
}

createServer( async ( req, res ) => {
	const match = req.url.match( /^\/article\/([a-z0-9-]+)\/?$/ );
	if ( ! match ) {
		res.writeHead( 404 ).end( 'Not found' );
		return;
	}

	try {
		const post = await getArticle( match[ 1 ] );
		if ( ! post ) {
			res.writeHead( 404 ).end( 'Not found' );
			return;
		}
		res.writeHead( 200, {
			'Content-Type': 'text/html; charset=utf-8',
			// Edge caching has to be set up by hand, too.
			'Cache-Control': 'public, max-age=60, stale-while-revalidate=300',
		} ).end( page( post ) );
	} catch {
		// API down or slow: fail fast rather than hang the reader.
		res.writeHead( 502 ).end( 'Upstream error' );
	}
} ).listen( PORT, () => {
	// eslint-disable-next-line no-console
	console.log(
		`Render service on http://localhost:${ PORT } (WordPress: ${ WP })`
	);
} );

function legacy_redirect_target( $path ) {
	if ( ! preg_match( '#^/article/([a-z0-9-]+)/?$#', $path, $match ) ) {
		return null;
	}

	// Core's get_page_by_path() is cached since WordPress 6.1, so VIP deprecated
	// its wpcom_vip_get_page_by_path() wrapper. Use core.
	$post = get_page_by_path( $match[1], OBJECT, 'post' );

	return ( $post && 'publish' === $post->post_status ) ? get_permalink( $post ) : null;
}

/**
 * Issue the 301 before WordPress decides it's a 404.
 *
 * @return void
 */
function redirect_legacy_urls() {
	if ( ! is_404() ) {
		return;
	}

	$path   = wp_parse_url( esc_url_raw( wp_unslash( $_SERVER['REQUEST_URI'] ?? '' ) ), PHP_URL_PATH ); // phpcs:ignore WordPressVIPMinimum.Variables.ServerVariables.UserControlledHeaders
	$target = legacy_redirect_target( (string) $path );

	if ( $target ) {
		wp_safe_redirect( $target, 301, 'News UK headless migration' );
		exit;
	}
}

function sync_products() {
	$since    = get_option( CURSOR_KEY, '' );
	$response = wp_remote_post(
		endpoint(),
		[
			'timeout' => 3, // Short: a slow API must not tie up PHP workers.
			'headers' => [ 'Content-Type' => 'application/json' ],
			'body'    => wp_json_encode(
				[
					'query'     => QUERY,
					'variables' => [ 'since' => $since ? $since : null ],
				]
			),
		]
	);

	$products = parse_response( $response );

	if ( is_wp_error( $products ) ) {
		/**
		 * Hook for logging/alerting (New Relic, Slack...). Readers never see it.
		 */
		do_action( 'news_uk_catalogue_sync_failed', $products );
		return $products;
	}

	$cursor = $since;
	foreach ( $products as $item ) {
		save_product( $item );
		$cursor = max( $cursor, (string) $item['updatedAt'] );
	}

	// Only move the cursor after everything saved, so a crash re-fetches.
	update_option( CURSOR_KEY, $cursor, false );

	return count( $products );
}

/**
 * Turn an HTTP response into a list of products, or a WP_Error for every way it can fail.
 *
 * @param array|\WP_Error $response wp_remote_post() result.
 * @return array|\WP_Error
 */
function parse_response( $response ) {
	if ( is_wp_error( $response ) ) {
		return $response; // Timeout, DNS, connection refused.
	}

	$code = wp_remote_retrieve_response_code( $response );
	if ( 200 !== $code ) {
		return new \WP_Error( 'news_uk_catalogue_http', 'Catalogue API returned HTTP ' . $code );
	}

	$body = json_decode( wp_remote_retrieve_body( $response ), true );
	if ( ! is_array( $body ) ) {
		return new \WP_Error( 'news_uk_catalogue_json', 'Catalogue API returned invalid JSON' );
	}

	// GraphQL reports errors with HTTP 200 and an "errors" array.
	if ( ! empty( $body['errors'] ) ) {
		return new \WP_Error( 'news_uk_catalogue_graphql', $body['errors'][0]['message'] ?? 'GraphQL error' );
	}

	if ( ! isset( $body['data']['products'] ) || ! is_array( $body['data']['products'] ) ) {
		return new \WP_Error( 'news_uk_catalogue_shape', 'Unexpected response shape' );
	}

	return $body['data']['products'];
}

function get_product( $external_id ) {
	$external_id = sanitize_key( $external_id );
	$cached      = wp_cache_get( 'product_' . $external_id, CACHE_GROUP );

	if ( false !== $cached ) {
		return $cached ? $cached : null; // Empty array = cached "not found".
	}

	$ids = get_posts(
		[
			'post_type'        => POST_TYPE,
			'name'             => $external_id,
			'post_status'      => 'publish',
			'posts_per_page'   => 1,
			'fields'           => 'ids',
			'no_found_rows'    => true,
			'suppress_filters' => false,
		]
	);

	$product = $ids ? [
		'id'       => $external_id,
		'name'     => get_the_title( $ids[0] ),
		'price'    => (float) get_post_meta( $ids[0], 'price', true ),
		'currency' => get_post_meta( $ids[0], 'currency', true ),
		'url'      => get_post_meta( $ids[0], 'url', true ),
	] : [];

	wp_cache_set( 'product_' . $external_id, $product, CACHE_GROUP, HOUR_IN_SECONDS );

	return $product ? $product : null;
}

function save_product( array $item ) {
	$slug     = sanitize_key( $item['id'] );

		[
			'post_type'        => POST_TYPE,
			'name'             => $slug,
			'post_status'      => 'any',
			'posts_per_page'   => 1,
			'fields'           => 'ids',
			'no_found_rows'    => true,

		[
			'ID'          => $existing ? $existing[0] : 0,
			'post_type'   => POST_TYPE,
			'post_status' => 'publish',
			'post_name'   => $slug,

			],
		],
		true
	);

	wp_cache_delete( 'product_' . $slug, CACHE_GROUP );

	return $post_id;

function remember( $key, $ttl, callable $generate ) {
	$entry = wp_cache_get( $key, GROUP );

	if ( is_array( $entry ) && $entry['fresh_until'] > time() ) {
		return $entry['value']; // Fresh: the common case.
	}

	// wp_cache_add only succeeds if the key does not exist: an atomic lock.
	$got_lock = wp_cache_add( $key . ':lock', 1, GROUP, 30 );

	if ( ! $got_lock && is_array( $entry ) ) {
		return $entry['value']; // Someone else is rebuilding: serve stale.
	}

	$value = $generate();
	wp_cache_set(
		$key,
		[
			'value'       => $value,
			'fresh_until' => time() + $ttl,
		],
		GROUP,
		// Keep stale copies around long enough to serve during rebuilds. The sniff
		// can't evaluate a variable; with the 60s live-blog TTL this is 600s.
		$ttl * 10 // phpcs:ignore WordPressVIPMinimum.Performance.LowExpiryCacheTime.CacheTimeUndetermined
	);
	wp_cache_delete( $key . ':lock', GROUP );

	return $value;
}

function record_view( $post_id ) {
	$key = 'views_' . (int) $post_id;

	if ( false === wp_cache_add( $key, 1, GROUP, DAY_IN_SECONDS ) ) {
		return (int) wp_cache_incr( $key, 1, GROUP );
	}

	$pending   = (array) wp_cache_get( 'pending_ids', GROUP );
	$pending[] = (int) $post_id;
	wp_cache_set( 'pending_ids', array_unique( $pending ), GROUP, DAY_IN_SECONDS );

	return 1;
}

/**
 * Cron: flush pending view counts to post meta in one batch.
 *
 * @return void
 */
function flush_views() {
	$pending = (array) wp_cache_get( 'pending_ids', GROUP );
	wp_cache_delete( 'pending_ids', GROUP );

	foreach ( $pending as $post_id ) {
		$count = (int) wp_cache_get( 'views_' . $post_id, GROUP );
		wp_cache_delete( 'views_' . $post_id, GROUP );

		if ( $count > 0 ) {
			update_post_meta( $post_id, 'news_uk_views', (int) get_post_meta( $post_id, 'news_uk_views', true ) + $count );
		}
	}
}

function merge( $shared, $override ) {
	if ( null === $shared ) {
		return null; // Overrides alone are orphans: nothing to show.
	}

	$override = array_filter( (array) $override, fn( $value ) => '' !== $value && null !== $value );

	return array_merge( $shared, array_intersect_key( $override, $shared ) );
}

/**
 * Product as this site should show it.
 *
 * @param string $id Product ID.
 * @return array|null
 */
function get_product( $id ) {
	$key    = 'product_' . $id . '_' . version( 'shared' ) . '_' . version( 'site' );
	$cached = wp_cache_get( $key, 'news_uk_network' . get_current_blog_id() );

	if ( false !== $cached ) {
		return $cached;
	}

	$shared   = get_site_option( SHARED_KEY, [] )[ $id ] ?? null;
	$override = get_option( OVERRIDE_KEY, [] )[ $id ] ?? null;
	$product  = merge( $shared, $override );

	wp_cache_set( $key, $product, 'news_uk_network' . get_current_blog_id(), HOUR_IN_SECONDS );

	return $product;
}

<?php
/**
 * Q31: the repair logic, kept free of WP-CLI so it can be unit tested.
 *
 * @package News_UK_Practice
 */

namespace News_UK_Practice\Q31;

/**
 * Finds and repairs posts whose standfirst was lost in the migration
 * (the old app kept it in the excerpt).
 */
class Standfirst_Repair {

	/**
	 * Posts per batch: bounded memory, never posts_per_page => -1.
	 */
	const BATCH = 100;

	/**
	 * One batch of affected posts, after a given ID (keyset pagination: stable
	 * even while we write, unlike OFFSET).
	 *
	 * @param int $after_id Last ID of the previous batch.
	 * @return \WP_Post[]
	 */
	public function find_batch( $after_id = 0 ) {
		global $wpdb;

		// phpcs:ignore WordPress.DB.DirectDatabaseQuery -- One-off repair, indexed columns, batched.
		$ids = $wpdb->get_col(
			$wpdb->prepare(
				"SELECT p.ID FROM {$wpdb->posts} p
				LEFT JOIN {$wpdb->postmeta} m ON m.post_id = p.ID AND m.meta_key = 'news_uk_standfirst'
				WHERE p.post_type = 'post' AND p.post_status IN ('publish','future','draft')
				AND p.post_excerpt <> '' AND ( m.meta_value IS NULL OR m.meta_value = '' )
				AND p.ID > %d ORDER BY p.ID ASC LIMIT %d",
				$after_id,
				self::BATCH
			)
		);

		return array_map( 'get_post', array_map( 'intval', $ids ) );
	}

	/**
	 * Audit: every affected post, as rows for a report. Changes nothing.
	 *
	 * @return array[] Rows: ID, title, proposed standfirst.
	 */
	public function audit() {
		$rows  = [];
		$after = 0;

		do {
			$batch = $this->find_batch( $after );
			foreach ( $batch as $post ) {
				$rows[] = [
					'ID'         => $post->ID,
					'title'      => $post->post_title,
					'standfirst' => $this->proposed_standfirst( $post ),
				];
				$after  = $post->ID;
			}
			// A full batch means there may be more; a short one means we're done.
			$has_more = count( $batch ) === self::BATCH;
		} while ( $has_more );

		return $rows;
	}

	/**
	 * What we would write.
	 *
	 * @param \WP_Post $post Post.
	 * @return string
	 */
	public function proposed_standfirst( \WP_Post $post ) {
		return sanitize_text_field( wp_strip_all_tags( $post->post_excerpt ) );
	}

	/**
	 * Repair. Dry run unless $apply is true.
	 *
	 * @param bool          $apply   Write changes.
	 * @param callable|null $logger  Called with ( ID, value ) for each post.
	 * @return int Posts (that would be) repaired.
	 */
	public function repair( $apply = false, ?callable $logger = null ) {
		$count = 0;

		foreach ( $this->audit() as $row ) {
			if ( $apply ) {
				update_post_meta( $row['ID'], 'news_uk_standfirst', $row['standfirst'] );
				update_post_meta( $row['ID'], '_news_uk_repaired', gmdate( 'c' ) ); // Audit trail for rollback.
			}
			if ( $logger ) {
				$logger( $row['ID'], $row['standfirst'] );
			}
			++$count;
		}

		return $count;
	}
}

function suggest_standfirst( $title, $content ) {
	if ( '' === api_key() ) {
		return new \WP_Error( 'news_uk_ai_not_configured', __( 'AI summaries are not configured on this environment.', 'news-uk' ), [ 'status' => 503 ] );
	}

	$response = wp_remote_post(
		(string) apply_filters( 'news_uk_ai_endpoint', API_URL ),
		[
			// VIP flags timeouts over 3s because a slow API would tie up PHP workers
			// serving readers. This call is only made from an editor's REST request
			// (never on a front-end page), and LLM responses take several seconds.
			'timeout' => 60, // phpcs:ignore WordPressVIPMinimum.Performance.RemoteRequestTimeout.timeout_timeout
			'headers' => [
				'Content-Type'      => 'application/json',
				'x-api-key'         => api_key(),
				'anthropic-version' => API_VERSION,
				// If a safety classifier declines, the API retries on a suitable model.
				'anthropic-beta'    => 'server-side-fallback-2026-07-01',
			],
			'body'    => wp_json_encode(
				[
					'model'         => MODEL,
					'max_tokens'    => 4000,
					'fallbacks'     => 'default',
					'output_config' => [ 'effort' => 'low' ], // Short, simple task.
					'system'        => SYSTEM_PROMPT,
					'messages'      => [
						[
							'role'    => 'user',
							'content' => "Title: {$title}\n\nArticle:\n{$content}",
						],
					],
				]
			),
		]
	);

	return parse_response( $response );
}

/**
 * Turn the HTTP response into the suggestion text, or a WP_Error.
 *
 * @param array|\WP_Error $response wp_remote_post() result.
 * @return string|\WP_Error
 */
function parse_response( $response ) {
	if ( is_wp_error( $response ) ) {
		return new \WP_Error( 'news_uk_ai_http', $response->get_error_message(), [ 'status' => 502 ] );
	}

	$code = wp_remote_retrieve_response_code( $response );
	$body = json_decode( wp_remote_retrieve_body( $response ), true );

	if ( 200 !== $code ) {
		$status = 429 === $code ? 429 : 502; // Pass rate limits through so the UI can say "try later".
		return new \WP_Error( 'news_uk_ai_api', $body['error']['message'] ?? 'API error ' . $code, [ 'status' => $status ] );
	}

	// Always check why the model stopped before reading the content.
	$stop_reason = $body['stop_reason'] ?? '';
	if ( 'refusal' === $stop_reason ) {
		return new \WP_Error( 'news_uk_ai_refusal', __( 'The model declined to summarise this article.', 'news-uk' ), [ 'status' => 422 ] );
	}
	if ( 'end_turn' !== $stop_reason ) {
		return new \WP_Error( 'news_uk_ai_incomplete', 'Unexpected stop_reason: ' . $stop_reason, [ 'status' => 502 ] );
	}

	// Content is a list of blocks (thinking blocks may come first): keep the text ones.
	$text = '';
	foreach ( (array) ( $body['content'] ?? [] ) as $block ) {
		if ( 'text' === ( $block['type'] ?? '' ) ) {
			$text .= $block['text'];
		}
	}

	// Untrusted output: plain text only, capped.
	$text = wp_trim_words( sanitize_text_field( $text ), 40, '…' );

	return '' === $text ? new \WP_Error( 'news_uk_ai_empty', 'Empty response', [ 'status' => 502 ] ) : $text;
}

function approve_draft( \WP_REST_Request $request ) {
	$post_id = (int) $request['id'];
	$draft   = get_post_meta( $post_id, DRAFT_META, true );

	if ( '' === $draft ) {
		return new \WP_Error( 'news_uk_ai_no_draft', __( 'There is no suggestion to approve.', 'news-uk' ), [ 'status' => 409 ] );
	}

	update_post_meta( $post_id, 'news_uk_standfirst', $draft );
	update_post_meta( $post_id, APPROVED_META, get_current_user_id() ); // Who signed it off.
	delete_post_meta( $post_id, DRAFT_META );

	return [ 'published' => get_post_meta( $post_id, 'news_uk_standfirst', true ) ];
}

	 *
	 * @var array[]

	 *
	 * @var int
	 */

	/**
	 * Fake key, an editor, a post, and a default "API".
	 */
	public function set_up() {
		parent::set_up();
		wp_cache_flush_group( 'news_uk_ai' );
		remove_all_filters( 'news_uk_ai_endpoint' );
		add_filter( 'news_uk_ai_api_key', fn() => 'test-key' );

				'post_title'   => 'Rates decision',

			]
		);
		$this->fake_api( 200, $this->message( 'end_turn', 'The Bank of England held rates at 4%.' ) );

	/**
	 * A Messages API response body.
	 *
	 * @param string $stop_reason Stop reason.
	 * @param string $text        Text block.
	 * @return array
	 */
	private function message( $stop_reason, $text ) {
		return [
			'type'        => 'message',
			'content'     => [
				[
					'type'     => 'thinking',
					'thinking' => '',
				],
				[
					'type' => 'text',
					'text' => $text,
				],
			],
			'stop_reason' => $stop_reason,
		];
	}

	/**
	 * Make the API return $code / $body.
	 *
	 * @param int   $code HTTP status.
	 * @param array $body JSON body.
	 */
	private function fake_api( $code, $body ) {
		remove_all_filters( 'pre_http_request' );
		add_filter(
			'pre_http_request',
			function ( $pre, $args, $url ) use ( $code, $body ) {
				$this->calls[] = [
					'url'  => $url,
					'args' => $args,
					'body' => json_decode( $args['body'], true ),
				];
				return [
					'response' => [ 'code' => $code ],
					'body'     => wp_json_encode( $body ),
				];
			},
			10,
			3
		);
	}

	/**
	 * Call a route.
	 *
	 * @param string $suffix '' or '/approve'.
	 * @return \WP_REST_Response
	 */
	private function post( $suffix = '' ) {
		return rest_do_request( new WP_REST_Request( 'POST', '/news-uk/v1/ai-summary/' . $this->post_id . $suffix ) );
	}

		$this->assertSame( $status, $this->post()->get_status() );

	 * @return array

	 * Output is untrusted: HTML stripped, length capped.

	 * Per-user rate limit protects cost.

			wp_update_post(
				[
					'ID'           => $this->post_id,

			$this->assertSame( 200, $this->post()->get_status() );

				'ID'           => $this->post_id,
				'post_content' => 'Version 6.',

	}

	 * No key configured: clear 503, no HTTP call.

	public function test_not_configured() {
		remove_all_filters( 'news_uk_ai_api_key' );

		$this->assertSame( 503, $this->post()->get_status() );
		$this->assertCount( 0, $this->calls );
	}

Blocks and the editor

M1.What are the differences between apiVersion 1, 2 and 3 in block.json?

"Each version moved more responsibility to the block itself. Version 3 is the current one: it's what lets the editor run in an iframe."

  • 1 (legacy): the editor wrapped every block in its own extra <div>. Blocks didn't control their outer element.
  • 2 (WP 5.6): the block's own element is the wrapper, via useBlockProps(). Lighter DOM, and the editor markup matches the front end.
  • 3 (WP 6.3): same as 2, plus the block declares it works in the iframed editor (its styles and scripts load inside the iframe). The editor only switches to the iframe when every block on the page is v3, and WordPress 6.9 logs a deprecation for anything lower.
In this repoEvery block uses "apiVersion": 3. The Jest run actually printed the 6.9 warning for a test block registered without it (Q3), which is a nice detail to mention.
Remember it as"Editor wraps, block wraps, block works in the iframe."

M2.Explain block.json in depth. Which fields matter most, and why register blocks from metadata?

"block.json is the block's single source of truth, read by both PHP and JS. Registering from metadata means WordPress registers the assets, loads them only where the block is used, and handles translations for me."

  • Identity: name (never rename it: it's stored in every post), title, category, apiVersion, textdomain.
  • Data: attributes, usesContext / providesContext.
  • Behaviour: supports (colour, spacing, typography, interactivity, html), parent / ancestor / allowedBlocks.
  • Assets: editorScript, script, viewScript, viewScriptModule, style, editorStyle, and render for a PHP render file.
  • Why metadata: one definition instead of two that drift apart; front-end assets enqueue only on pages that contain the block; strings in block.json are translatable; the block can be listed in the Block Directory. On sites with many blocks, WordPress 6.7+ can load them all from one compiled manifest (wp_register_block_metadata_collection()) for speed.
In this repoq01-article-teaser/index.js explains each key of its block.json in comments (JSON can't hold comments).

M3.How do block attributes work? Where are they stored and what are the common pitfalls?

"Attributes are the block's data, typed in block.json. Most are stored as JSON in the block's comment delimiter; some are sourced from the saved HTML."

  • Storage: no source means JSON in <!-- wp:name {...} -->. With a source (attribute, html, text, query), the value is parsed out of the saved markup instead. Post meta is the third place, now done with Block Bindings (Q4), not the old meta source.
  • Pitfall: defaults aren't saved. A value equal to the default isn't written to the comment, so changing a default later silently changes every old block that used it.
  • Pitfall: sourced attributes are tied to markup. Change the selector or the save markup and old content breaks, so you need a deprecation (Q3).
  • Pitfall: types. A string saved into an integer attribute fails validation. Convert input first (Q1 parseInt) or use TypeScript (Q21).
  • Pitfall: wrong home for data. Attributes live inside post_content, so they can't be queried or reused across posts. Data that needs that belongs in post meta.

M4.How do you use InnerBlocks? How do you control what can be nested and how it is saved?

"InnerBlocks makes my block a container for other blocks. I control what goes in with allowedBlocks, template and templateLock, and in save I output InnerBlocks.Content."

  • Edit: useInnerBlocksProps( useBlockProps(), { allowedBlocks, template, templateLock } ) puts the wrapper and the drop zone on one element.
  • Controlling nesting: allowedBlocks (which children), template (what a new block starts with), templateLock: "all", "insert" or "contentOnly" (text editable, layout locked). From the child side, block.json parent / ancestor.
  • Save: static blocks save useInnerBlocksProps.save(). Dynamic blocks save only <InnerBlocks.Content /> and render.php receives the children as $content.

M5.How does server-side rendering work for blocks, and how do you preview dynamic blocks in the editor?

"A dynamic block's save returns null; on every request WordPress calls its render callback or render.php with the attributes, content and block instance. In the editor I either use ServerSideRender or rebuild the preview in React."

  • On the server: do_blocks() parses post_content, and for each dynamic block calls the render with $attributes, $content and $block (which carries context such as postId).
  • Preview option 1, ServerSideRender: the editor calls the block-renderer REST endpoint and shows the real PHP output. Exact match, but one request per change.
  • Preview option 2, React: fetch the data with useSelect and draw it. Instant and interactive, but two implementations to keep in step.
  • Gotcha: a template in the Site Editor has no specific post, so context-dependent blocks need a placeholder there.

M6.How do you use block patterns? What are synced patterns and pattern overrides?

"A pattern is a ready-made group of blocks editors insert and then own. A synced pattern is one shared copy: edit it once, it changes everywhere. Pattern overrides let editors change chosen parts of a synced pattern per instance."

  • Registering: drop a PHP file with a header into the theme's patterns/ folder (auto-registered), or call register_block_pattern() from a plugin.
  • Unsynced (regular): inserted as plain blocks, no link back. Good for starting layouts.
  • Synced (formerly "reusable blocks", stored as wp_block posts): one source, so a change shows up wherever it's used.
  • Pattern overrides (6.6+): inside a synced pattern, mark blocks as overridable (e.g. a heading and an image). The layout stays shared, and each instance has its own text. It's built on Block Bindings with the core/pattern-overrides source.
In this repoQ7: the "Key points" pattern (core blocks only) and the theme's patterns/hero.php.

M7.What are your best practices for block development?

"Core first; block.json as the source of truth; blocks in a plugin; dynamic for data; supports instead of custom controls; escape late; accessible markup; and tests at the right layer."

  • Try variations, styles, patterns and bindings before a custom block (Q7, Q8).
  • apiVersion 3, useBlockProps, @wordpress/components for UI, translated strings.
  • Dynamic rendering for anything data-driven; cache expensive queries (Q2, Q15).
  • Small attributes, typed; never rename a block; deprecations for static markup changes (Q3).
  • Load front-end JS only where needed (Interactivity API, viewScriptModule, Q5).
  • PHPUnit for render.php, Jest for edit/save, one Playwright journey; PHPCS + ESLint in CI.

M8.What can clients edit within the Site Editor?

"Anyone with the edit_theme_options capability (administrators by default) can edit templates, template parts, global styles, navigation menus, patterns and pages. Editors normally can't open it at all."

  • Global Styles: colours, typography and spacing, within what theme.json allows.
  • Templates and template parts: header, footer, single post and so on.
  • Navigation, patterns, pages (page content can also be edited inside the Site Editor).
  • The theme decides the limits: theme.json can turn off custom colours or font sizes, and block locking can fix the layout.

M9.Explain the template schema, and why template-level editing is typically restricted from clients.

"Templates are block markup: files in the theme's templates/ and parts/ folders, chosen by the template hierarchy. A customised copy is saved as a wp_template post that overrides the file. Template edits affect every page of that type at once, so they're kept to a few trusted people."

  • Schema: templates/single.html, templates/index.html, custom templates listed in theme.json customTemplates, parts in parts/ declared in templateParts. Edits go into the database (wp_template / wp_template_part) and win over the file until reset.
  • Why restrict: one change hits thousands of articles, including ad slots, analytics, structured data and accessibility landmarks. Database copies also drift from the theme code that's reviewed and deployed.
  • How: capabilities (only admins get edit_theme_options), locked blocks, contentOnly template locking, theme.json restrictions, and keeping template changes in code reviews.

Testing

M10.Explain the general concepts of unit testing.

"A unit test checks one small piece of behaviour in isolation, quickly and the same way every time, so I can change code without fear."

  • Arrange, Act, Assert: set up, run the one thing, check the result.
  • Isolation: replace slow or external dependencies with test doubles (stubs return canned data, mocks check how they were called, fakes are simple working versions).
  • Test behaviour, not implementation: assert on outputs and effects, so a refactor doesn't break the tests.
  • Fast and deterministic: no network, no real time, no shared state between tests.
  • Coverage is a signal, not the goal: it shows what's untested, not whether the tests are good.

M11.Which JavaScript unit testing libraries do you use?

"Jest as the runner (through @wordpress/scripts), React Testing Library to render components the way a user sees them, user-event for interactions and jest-dom for readable assertions."

  • @wordpress/jest-preset-default sets up jsdom and Babel; @wordpress/jest-console fails a test on unexpected console warnings.
  • RTL's rule: query by role and label (getByRole( 'checkbox', { name: 'Show image' } )), which also checks accessibility.

M12.How do you write and maintain unit tests over time?

"Tests are code: reviewed in the same PR, kept fast, fixed or deleted when they rot, and every bug fix comes with a test that would have caught it."

  • Run them in CI on every PR; a red test blocks the merge.
  • Fix flaky tests immediately; a flaky suite gets ignored.
  • Test behaviour so refactors don't need test rewrites; use data providers to cover edge cases in one test.
  • Delete tests for removed features; keep test names readable as documentation.

M13.How do you unit test PHP code without loading WordPress?

"Keep business logic in pure functions or classes that don't call WordPress, and test those with plain PHPUnit. Where code must call WordPress functions, mock them with Brain Monkey or WP_Mock."

  • Mocking WordPress: Brain Monkey or WP_Mock stub get_option(), apply_filters() and friends, and let you assert that hooks were added.

M14.How do you test block registration, save output, transforms and deprecations in Jest?

"Register the block in the test, then use the @wordpress/blocks API exactly as the editor does: getSaveContent for save, serialize and parse for round trips, switchToBlockType for transforms, and parsing old markup for deprecations."

  • Registration: registerBlockType( name, settings ), then getBlockType( name ) has the expected attributes and supports.
  • Save: getSaveContent( name, attributes ) returns the exact HTML.
  • Round trip: parse( serialize( block ) ) must give isValid: true.
  • Transforms: switchToBlockType( createBlock( 'core/paragraph', {...} ), 'my/block' ).
  • Deprecations: parse markup produced by the old version; assert it's valid and the attributes were migrated.

M16.How do you approach WordPress integration testing?

M35.Explain edge caching.

M36.What is the difference between object caching and transients?

"The object cache is a key-value cache for anything, and it only persists between requests with a drop-in such as Memcached. Transients are a cache API with an expiry that falls back to the database when there's no persistent object cache."

  • With Memcached (VIP), transients are stored in the object cache, so in practice they're the same thing with an expiry.
  • Either can disappear early, so always handle a miss.
  • Prefer wp_cache_* with a group on VIP; use transients when the code must also work on hosts without an object cache.

M37.Where does the object cache store its data?
